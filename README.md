## Задание 1. Производитель–потребитель

**(а) Семафоры + мьютекс.**
- `empty = Semaphore(5)` — число свободных мест, `full = Semaphore(0)` — число элементов.
- Производитель: `empty.acquire()` → под мьютексом кладёт элемент → `full.release()`.
- Потребитель: `full.acquire()` → под мьютексом забирает → `empty.release()`.
- Семафоры считают места и элементы, мьютекс защищает сами поля буфера (`head`, `tail`, `count`) от одновременного изменения.

**(б) Мьютекс + условная переменная.**
- `threading.Condition` содержит мьютекс. Производитель ждёт, `while` буфер полон; потребитель ждёт, `while` буфер пуст.
- Одна условная переменная обслуживает оба условия («не полон» и «не пуст»), поэтому используется `notify_all()`: иначе `notify()` мог бы разбудить поток «не того типа», и все остались бы ждать.

Завершение: после окончания производителей в буфер кладутся «ядовитые пилюли» (`STOP`), по одной на потребителя.
Блокировки захватываются только через `with`, поэтому освобождаются даже при исключении. Критическая секция узкая — только операции с буфером.

## Задание 2. Проверка корректности (в коде, а не «на глаз»)

`RingBuffer` при каждой операции проверяет инварианты и записывает нарушения: **переполнение** (`count` > 5) и **чтение из пустого буфера** (`count` < 0). После работы тест проверяет, что каждый элемент 0…999 потреблён **ровно один раз** (нет дубликатов и потерь) и что программа не зависла (таймаут 10 с).
Чтобы гонки проявлялись чаще, интервал переключения потоков уменьшен: `sys.setswitchinterval(1e-5)`.

**Результат:** обе правильные версии — 3 прогона из 3: потреблено 1000 из 1000, дубликатов 0, потерь 0, нарушений 0, `OK` (см. `pc_sem.txt`, `pc_cond.txt`).

## Задание 3. Барьер

`Barrier.wait()`: поток увеличивает счётчик пришедших; последний (четвёртый) увеличивает номер **поколения**, обнуляет счётчик и вызывает `notify_all()`; остальные ждут, `while` поколение не сменилось. Номер поколения позволяет использовать один барьер для всех трёх фаз.
Проверка в коде: в общем журнале все записи «закончил фазу p» стоят раньше любой записи «начал фазу p+1». Результат: фаза 1→2 и 2→3 — `OK`.

## Задание 4. «Потерянное пробуждение»: if вместо while

В `pc_cond_if.py` проверка условия перед `wait()` сделана через `if`. Результат — **ошибки в 5 из 5 прогонов**: переполнение буфера (`в буфере уже 5, кладём 1`), чтение пустого буфера, потеряны сотни элементов (например, 685 из 1000).

**При каком чередовании это ломается:**
1. Буфер полон (5 элементов). Все 3 производителя проверили `if count == 5` и уснули в `wait()`.
2. Потребитель забрал 1 элемент (стало 4) и вызвал `notify_all()` — проснулись **все три** производителя.
3. Они по очереди захватывают мьютекс. Первый кладёт элемент (стало 5). Второй и третий **не проверяют условие заново** (`if` уже пройден до сна) и тоже кладут: 6, 7 — переполнение. Новые элементы записываются поверх ещё не прочитанных — данные теряются.
4. Симметрично с потребителями: оба ждут на пустом буфере, производитель кладёт 1 элемент и будит обоих; первый забирает его, второй читает из пустого буфера.

Кроме того, `wait()` может завершиться и без `notify` (ложное пробуждение), а между `notify` и захватом мьютекса проснувшимся другой поток может успеть изменить состояние. Поэтому после пробуждения условие **всегда** нужно проверять заново — в цикле `while`. Исправленная версия — `pc_cond.py`.

## Контрольные вопросы

**1. Чем семафор со значением 1 отличается от мьютекса на практике?**
У мьютекса есть **владелец**: освобождать его должен тот поток, который захватил (в pthreads это проверяется, бывают рекурсивные мьютексы и наследование приоритета). У семафора владельца нет — `release()` может вызвать любой поток, поэтому семафор подходит для **сигнализации** между потоками (как `full`/`empty` в задании). Ошибочный лишний `release()` увеличит семафор до 2 — и в критическую секцию войдут двое (от этого защищает `BoundedSemaphore`). Мьютекс — для взаимного исключения, семафор — для подсчёта ресурсов и сигналов.

**2. Почему условную переменную нельзя использовать без мьютекса?**
Условие (например, «буфер пуст») — это общие данные, и их проверка вместе с засыпанием должна быть **атомарной**. Без мьютекса возможно: поток проверил «пусто», но не успел уснуть; другой поток положил элемент и вызвал `notify` — сигнал никого не разбудил (потерян), и первый поток уснул навсегда. `wait()` атомарно освобождает мьютекс и засыпает, а при пробуждении снова захватывает мьютекс — поэтому проверять условие и ждать можно только под мьютексом.
